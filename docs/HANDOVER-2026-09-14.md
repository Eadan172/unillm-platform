## 二、两个 P2 边界：实测把上一轮的结论推翻了

**必须更正**：上一轮我写「两个 P2 边界校验均已实现」，这是**误判**。
本轮用 11 个服务层用例 + 3 个 HTTP 层用例重跑，结论如下。

### P2-① 空文件导入 → 确实已实现，且覆盖 5/6 场景

| 用例 | 实测结果 |
|---|---|
| `[]` 空数组 | ✅ 拒绝 |
| 0 字节 `.jsonl` | ✅ 拒绝 |
| 0 字节 `.csv` | ✅ 拒绝 |
| JSONL 仅空行 | ✅ 拒绝 |
| CSV 仅表头 | ✅ 拒绝 |
| **0 字节 `.json`** | ⚠️ 拒绝，但走的是**另一条路** |

前 5 个联动返回中文「文件中没有任何有效记录」。但 0 字节 `.json` 在
`json.load()` 就抛了英文 `JSONDecodeError`，**根本没走到空文件校验**。

### P2-② `label` 字段 → 不是「校验缺失」，是「额外键被静默忽略」

`[{"instruction":"分类","output":"正面","label":99}]` → **正常导入 1 条**，`label` 被丢掉且无提示。

所以平台的问题不是「缺了 label 的域校验」，而是**根本不认 `label` 这个字段**。
这属于「宽容」而非「缺陷」，但用户若把 `output` 误写成 `label`，会得到 0 条内容记录——
这一点值得在文档里提示。

**教训：不要用旧笔记代替实测。** 本轮是重跑全部用例才拿到真相的。

## 三、实测挖出的真缺口（比那两个 P2 更值得修）—— 已修

| 缺口 | 旧表现 | 严重度 |
|---|---|---|
| **带 BOM 的 `.json`/`.jsonl` 被拒** | `Unexpected UTF-8 BOM (decode using utf-8-sig)` | **P1** |
| **GBK/GB18030 文件被拒** | `'utf-8' codec can't decode byte 0xb7` | **P1** |
| 0 字节 `.json` 报英文原始异常 | `Expecting value: line 1 column 1 (char 0)` | P2 |

前两条为什么是 P1 —— 它们**不是攻击面，而是日常使用必撞的墙**：

1. Windows 记事本「另存为 UTF-8」**必然写入 BOM**
2. 中文版 Excel 导出的 CSV/JSON 常为 GBK/GB18030

**根因**：JSON/JSONL 分支用裸 `utf-8` 打开，而**同一平台的 CSV 分支却用了 `utf-8-sig`**。
同平台两种格式宽容度不一致。

### 修复要点

1. 新增 `_read_text_with_fallback`：`utf-8-sig` → `gb18030` 依次尝试
2. **刻意不用 `errors="replace"` 静默容错** —— 那会把乱码写进数据集，比直接报错更糟。
   真正无法解码时**仍然拒绝**，只是换成中文可操作提示
3. JSON/JSONL 解析失败改为中文提示，并附**可定位的行列号**
4. 0 字节/纯空白 `.json` 前移，与其余空文件共用同一条文案
5. CSV 分支经 `io.StringIO` 复用同一读取路径，消除格式间差异
