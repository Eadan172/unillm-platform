# 情感二分类端到端测试案例

本目录是一个可直接复现的 **情感二分类（好评 / 差评）** 闭环案例，用来验证
UniLLM Platform 的「数据接入 → 标注 → 模型 → 推理 → 评测」全链路是否可用。

---

## 一、案例来源与许可说明（请先读这一节）

**重要且诚实的前提**：本目录下的 `train.jsonl` / `test.jsonl` **不是** ChnSentiCorp
的官方数据分发，而是**参照 ChnSentiCorp（中文酒店评论二分类）的数据格式，自行编写的、
用于演示与联调的样例数据**。

- **格式与官方一致**：同样采用"一条评论 + 一个二元标签"的结构，因此可以**无缝替换**为
  官方全量数据，脚本与流程无需任何改动。
- **官方来源**：ChnSentiCorp 出自
  [`https://github.com/SophonPlus/ChineseNlpCorpus`](https://github.com/SophonPlus/ChineseNlpCorpus)。
  如需真实训练/评测，请从该仓库获取官方数据并替换本目录的 jsonl（保持字段名不变即可）。
- **本样例数据完全自撰**：20 条训练 + 10 条测试，共 30 条中文评论，均为本次为案例手写，
  未复制任何第三方数据集内容。

> 之所以要显式标注这一点，是因为平台的产品底线是**绝不造假**：不能让读者误以为
> 这份自造样例是官方数据，也不能用自造数据的指标冒充公开基准成绩。

## 二、字段规范

每行一个 JSON 对象（JSONL），字段顺序为 `text` 在前、`label` 在后：

| 字段 | 类型 | 取值范围 | 说明 |
|---|---|---|---|
| `text` | string | 15~60 字自然中文评论 | 酒店/餐厅评论原文，UTF-8 |
| `label` | int | `0` = 差评，`1` = 好评 | 情感标签 |

`test_without_label.jsonl` 与 `test.jsonl` 逐行一一对应，仅**去掉 `label` 字段**，
用于模拟"只知道输入、需要模型预测"的推理场景。

文件要求：UTF-8 **无 BOM**，每行一个 JSON 对象，无空行。

### 与平台导入字段的映射（重要，请勿跳过）

本目录磁盘上的 jsonl 用的是案例原生字段 `{text, label}`；而**平台导入接口只识别**
`instruction/question`、`input/context`、`output/answer` 这 6 个内容字段。若把
`{text,label}` 原样上传，平台会（正确地）以 **400** 拒绝"无任何可识别内容字段"的文件。

因此 `run_case.py` 在**内存中**做一次**显式、可复现**的转换后再上传，磁盘文件保持原格式不变：

| 案例原生字段 | → 平台字段 | 规则 |
|---|---|---|
| `text` | `input` | 评论原文 |
| `label`(int) | `output` | `str(label)`，即 `"0"` / `"1"`，作为参考答案 |
| （无） | `instruction` | 固定任务指令 `下面这条酒店评论是好评（1）还是差评（0）？只回答 0 或 1。` |

这样既保留了案例与官方 ChnSentiCorp 一致的原生格式（便于替换为官方数据），
又满足平台的标准字段约定。转换细节见 `run_case.py` 的 `to_platform_records()`。

## 三、为什么选这个案例

1. **二元标签，对错可判定**：好评/差评只有两种结果，`exact_match` 与字符级 F1 的
   计算口径清晰，不存在"评分标准模糊"导致的争议。
2. **语义明确、贴近真实**：评论是自然语言，正负情感由整体语义而非单个词决定，
   能真实检验评测口径是否"算的是模型输出、而不是参考答案本身"。
3. **正负夹杂样本能暴露问题**：案例刻意加入了"位置很好但隔音差到没法睡"这类
   混合情感样本，能验证平台在挑战样本上的行为，而不是只会在模板句上打转。

## 四、数据构成

| 文件 | 条数 | 好评 | 差评 | 用途 |
|---|---|---|---|---|
| `train.jsonl` | 20 | 10 | 10 | 导入为训练数据集，并据此建标注任务 |
| `test.jsonl` | 10 | 5 | 5 | 导入为测试数据集（带标签） |
| `test_without_label.jsonl` | 10 | — | — | 去标签，用于推理 |

覆盖场景：房间与床品、隔音、前台服务、早餐、位置交通、卫生、价格、退房流程、
接机/打印等增值服务、空调与热水等硬件。

### 挑战样本（正负夹杂，重点标注）

以下 3 条刻意设计为**一句话里同时包含正负评价**，用来检验评测在困难样本上的表现：

| 所在文件 | 文本 | 真实标签 | 说明的问题 |
|---|---|---|---|
| `test.jsonl` | 位置很好但房间隔音差到没法睡，前台态度还行，整体只能算勉强及格。 | 1 | 前半句是优点、后半句是重缺点，整体语气偏"勉强接受"；考察模型是否能综合判断而非抓住单个关键词 |
| `test.jsonl` | 房间隔音真心不错，隔壁说话一点听不见，可早餐九点就收了，八点五十去几乎没吃的。 | 0 | 先扬后抑，且用了"真心不错"这种强正面词；负面（早餐）才是主诉，容易误导只看正面词的模型 |
| `test.jsonl` | 价格是真便宜，可卫生实在不敢恭维，枕套上有头发，地毯一股潮味，住得心里发毛。 | 0 | "真便宜"是正面信号，但整体是明确差评；考察是否被单一正面词带偏 |

> 备注：第 1 条标签为 `1`（勉强接受、整体略偏正面），是对"混合情感如何定标签"的一种
> 人为约定；替换为官方数据时以官方标注为准。

## 六、完整复现步骤

前置：已完成 `pip install -r requirements.txt`，且当前环境能启动服务。

```bash
# 步骤 0：安装依赖（首次）
pip install -r requirements.txt

# 步骤 1：启动服务（前台运行，保持这个终端不关）
#   未安装 vLLM 时会自动降级为 mock 后端，并打印 degraded=true
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 步骤 2：另开一个终端，运行案例脚本
#   Token 默认从 data/.api_token 自动读取；也可用 --token 显式指定
python examples/sentiment_case/run_case.py

# 步骤 3（可选）：指定别的服务地址或 Token
python examples/sentiment_case/run_case.py \
    --base-url http://127.0.0.1:8000 \
    --token <你的 Token>
```

脚本会依次执行并打印每一步的真实响应关键字段：

1. `POST /api/data/import` —— 把 `train.jsonl` 与 `test.jsonl` 的 `{text,label}` **转换为
   平台标准字段** `{instruction,input,output}` 后导入（见 §二 的映射表）
2. `POST /api/annotation/task` —— 为训练集创建标注任务
3. `POST /api/model/register` —— 注册模型 `sentiment-case-mock`
4. `POST /v1/completions` —— 对 `test_without_label.jsonl` 逐条推理
5. `POST /api/evaluate/create` + `/{id}/run` —— 对推理结果评测

最后输出一张汇总表（Exact Match / Char-F1 / 延迟 min·avg·p50·p95·max / 样本数）。

### 关于 mock 后端的读法（务必注意）

若 `/health` 返回 `degraded: true`，说明当前跑在 **mock 占位后端**上：

- 脚本会在汇总表**上方打印醒目提示**，明确本次验证的是**链路可用性**，而不是模型效果。
- mock 后端输出的是固定占位文本（以 `[MOCK]` 开头），**准确率必然极低（通常为 0）**。
  这是**正确行为**，不是平台算错了，也不是脚本漏样本。
- 若看到 mock 下准确率异常高，那才是 bug，应当排查。

### 幂等性

脚本对重复运行是**幂等友好**的：同名数据集、同名标注任务、同名模型若已存在，
会自动复用并打印"已存在 → 复用"，而不是报错。因此可以放心多次运行。

### 出错时的输出

任何非 2xx 响应，脚本都会打印服务端返回的统一错误契约三字段
`detail / error_code / hint`，便于定位（例如 Token 无效会打印
`[UNAUTHORIZED] 访问令牌无效`）。
